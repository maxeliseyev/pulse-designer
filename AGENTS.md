# AGENTS.md — Pulse Designer

Контракт проекта для людей и агентов. Спецификация и этот файл важнее
локальных удобств реализации.

## С чего начинать

Перед задачей прочитать:

1. этот файл;
2. [`docs/drum-synth-spec.md`](docs/drum-synth-spec.md);
3. [`docs/implementation-plan.md`](docs/implementation-plan.md);
4. последний документ в `docs/sessions/`, если он уже существует.

Если появится `docs/status.md`, он становится первым источником текущего
состояния, ветки и следующего шага.

Команды shell в проекте запускаются через `rtk`, например:

```bash
rtk git status
rtk rg -n "pattern" src tests
rtk make test
```

## Продуктовые границы

Первая версия — один MIDI-инструмент на инстанс:

- один осцилляторный источник и один шумовой источник;
- один стереовыход;
- параметры защёлкиваются в момент `note-on`;
- многоканальная партия строится несколькими инстансами в хосте.

В первую версию не добавлять:

- секвенсор и паттерны;
- мультитембральность и мультивыходы;
- воспроизведение сэмплов;
- встроенные эффекты;
- MIDI-выход;
- LFO и матрицу модуляций;
- choke-группы между инстансами.

## Неподлежащие компромиссу DSP-инварианты

1. MIDI обрабатывается сэмплово-точно внутри блока; события нельзя округлять к
   границе блока.
2. Огибающие считаются посэмплово и экспоненциально.
3. Ретриггер начинается от текущего значения огибающей, а не принудительно
   от нуля.
4. `Shape` и `Drive` работают с переключаемым oversampling 1x/2x/4x/8x;
   значение по умолчанию — 4x.
5. На выходе всегда включён DC blocker первого порядка на 10 Гц.
6. Фильтр шума — TPT/ZDF state-variable с непрерывным LP/BP/HP morph.
7. Все времена задаются в миллисекундах, частоты — в герцах. Результат не
   должен зависеть от частоты дискретизации.
8. В `processBlock` всегда используется `ScopedNoDenormals`.
9. В realtime-коде нельзя аллоцировать память, брать mutex или запускать
   офлайн-рендер preview.
10. Noise RNG должен быть детерминированным и продвигаться посэмплово.
11. Офлайн-рендер и realtime используют один `SynthEngine`, а не две версии
    алгоритма.

## Архитектура

Зависимости направлены вниз:

```text
src/plugin  →  src/dsp
tests       →  src/dsp и plugin smoke layer
```

`src/dsp` не должен знать о редакторе, окне, хосте или APVTS. JUCE допускается
в DSP только там, где это оправдано обязательным фильтром/oversampling и
решение зафиксировано в документации.

`src/plugin` содержит JUCE-адаптер:

- `AudioProcessor`;
- `prepareToPlay` и `processBlock`;
- APVTS и state persistence;
- MIDI segmentation;
- editor и waveform preview.

Новый DSP-блок сначала появляется в `src/dsp` и получает синтетический тест,
затем подключается к `PluginProcessor`.

## APVTS и состояние

- Parameter ID стабильны после первого публичного использования.
- Нельзя переименовывать или переиспользовать старый ID для другого смысла.
- Изменение формата state требует версии и migration path.
- Все параметры, влияющие на новый voice, latch-ятся при `note-on`.
- Preview читает snapshot и не обращается к состоянию audio thread напрямую.

## Тесты и критерии готовности

Для каждого DSP-изменения нужен тест, который способен упасть на известной
ошибке. Минимальный набор:

- envelopes и pitch sweep;
- все типы noise;
- filter morph;
- saturation и oversampling;
- DC blocker;
- retrigger через 5 мс;
- voice allocation;
- block-size invariance;
- sample-rate invariance;
- state round-trip;
- рендер всех factory presets.

Перед завершением задачи:

1. `make test` зелёный, когда Makefile появится.
2. Для GUI выполнены GUI-тесты и ручной Standalone smoke.
3. Для форматов выполнен host smoke в целевом хосте.
4. Нет NaN/Inf, неконтролируемого DC или необъяснимых пиков.
5. Изменённая архитектура отражена в `docs/`.

Реальные записи используются только локально для sound-quality gate. WAV/AIFF
и иные аудиоматериалы в репозиторий не добавляются.

## Порядок работы

- Один PR — один связный шаг плана или один фикс.
- Сначала DSP и тесты, затем plugin adapter, затем UI.
- UI не подключается до прохождения технического и звукового DSP gate.
- CLAP добавляется после стабильного VST3/AU/Standalone и использует тот же
  DSP/state слой.
- Нетривиальное решение фиксируется в `docs/decisions/` или
  `docs/sessions/`.

До первой публичной версии работа идёт от feature-веток в `main` через PR с
squash merge. Прямые изменения `main` не делать.

Рекомендуемый стиль коммитов — Conventional Commits:

```text
feat(dsp): add deterministic oscillator
test(plugin): cover midi block-size invariance
docs: record oversampling decision
```

## Стиль кода

- C++20 без GNU-расширений;
- `#pragma once`;
- 4 пробела, Allman и лимит 100 символов;
- не использовать `using namespace juce` в заголовках;
- комментарии объясняют только неочевидное решение или инвариант;
- не дублировать продуктовую логику между офлайн-рендером и realtime;
- не добавлять новую зависимость без фиксации причины и версии.
